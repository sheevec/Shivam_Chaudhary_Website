The problem

Multiple business units were running their own ingestion jobs against core banking, trading, market-data and CRM sources, each with different formats, different validation and no shared idea of when data was ready.

The result was slow daily batches, silent data loss when rows failed parsing, and analysts spending a large share of their week preparing data instead of using it.

Key engineering decisions

The choices that make the system reliable, not just fast.

Delta Lake as the storage layer

ACID on object storage, MERGE for change data, and time travel for safe backfills and RESTORE-based rollback.

Idempotency everywhere

Delta transaction IDs plus keyed MERGEs mean any replay (crash recovery, backfill, a cleared DAG run) converges instead of duplicating.

Quarantine over drops

Invalid rows land in typed Delta paths with a reason code. Silent data loss is treated as a bug.

Single-pass data quality

The DQ engine compiles a whole expectation suite into one Spark aggregate, so a full-table check costs one job regardless of how many rules it has.

Dedup before merge

A micro-batch can carry several versions of one key; keeping only the latest makes the MERGE cheaper and deterministic.

Policy-as-code PII

Declarative tokenise / mask / drop rules, reviewed like code; HMAC tokens keep joins working after masking.

def add_row_hash(df: DataFrame, exclude: tuple[str, ...] = ()) -> DataFrame:
    """xxhash64 over all non-meta business columns (deterministic order)."""
    cols = sorted(
        c
        for c in df.columns
        if not c.startswith(_META_PREFIX) and c not in _SCD_SYSTEM_COLUMNS and c not in exclude
    )
    return df.withColumn(
        "_row_hash", F.xxhash64(*[F.coalesce(F.col(c).cast("string"), F.lit("")) for c in cols])
    )
